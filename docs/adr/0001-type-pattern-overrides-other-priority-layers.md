# 型パターン成立時は他の優先度レイヤーを適用しない

Issue #3(https://github.com/5cd8/FGA/issues/3 、型パターンをバトルパイプラインに配線する)で、型パターン(`CardTypePatternSelector`)が成立したカードの並びに対して、既存のブレイブチェイン設定(`braveChainsPerWave`/`rearrangeCardsPerWave`)およびサーヴァント優先度(`useServantPriority`)を後段で適用すべきかが論点になった。両者とも型パターンが確定した並びを別の基準で組み直すため、ユーザーが位置ごとに明示指定した型の順序を崩しうる、という競合が起こりうる。

型パターンという機能の存在意義は「3枚の位置ごとに要求する型を厳密に指定できること」にあるため、成立時はブレイブチェイン設定・サーヴァント優先度のどちらも適用せず、型パターンが確定した並びをそのまま採用することに決定した。型パターンが不成立の場合は、これまでどおり両方とも適用される既存のフォールバックパイプライン(`FaceCardPriority.sort()` → `ApplyBraveChains.pick()`)を使う。

この決定に伴い、`CardTypePatternSelector.select()`へ渡す`cards`は`readCommandCards()`の生の並び(サーヴァント優先度・カード優先度でソートする前)を使う。

## Status

accepted

## 追記: コマンドコード優先はこの原則の対象外

「コマンドコード優先」(手札に同種別・同特効/耐性のカードが複数並んだ場合に、ユーザー指定のコマンドコードが付いている方を優先する機能)は、型パターン成立時にも`CardTypePatternSelector`の内部(同一要求型内の候補選択)で適用する。ここで除外しているのは「手札全体を型パターンとは別の基準で組み直す」ブレイブチェイン設定・サーヴァント優先度であり、コマンドコード優先は型パターンが要求する位置ごとの型順序を一切崩さず、「その型に該当する複数の実カードのどちらを選ぶか」だけを決める直交した判断のため、この原則の例外とする。
